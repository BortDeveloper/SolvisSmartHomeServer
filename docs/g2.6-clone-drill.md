## 1. Zweck

Belegt wiederholbar, dass sich der Zustand dieses **Repos** verlustfrei aus
einem Git-Bundle rekonstruieren lässt (Bundle → Clone → Verifikation von
Commit-Zahl und HEAD). Ein Backup zählt erst mit geübtem Restore als
Backup (Google SRE Book Kap. 26; NIST SP 800-53 Rev. 5 CA-7).

Der Drill deckt den **versionierten** Stand ab. Zwei Abgrenzungen sind seit
der Produktivaufnahme am 2026-08-13 ausdrücklich zu nennen, weil die frühere
Begründung („reiner mTLS-Client ohne Betriebs-State") in beiden Hälften
überholt ist:

- **Der Connector ist unter der produktiven Variante A kein mTLS-Client.**
  Er spricht **Klartext über `127.0.0.1:1883`** zum lokalen Mosquitto auf
  demselben Host; die mTLS-Strecke beginnt erst an der Bridge und liegt
  damit beim Broker-Host und dem Repo `ccu2mqtt` (as-built:
  `docs/runbooks/solvis-bridge-ransible.md`). Ein Client-Zertifikat besitzt
  dieser Connector nicht.
- **Nicht-versionierter Operator-State existiert sehr wohl** — seit dem
  Produktivbetrieb auf `ransible`: die installierte `base.xml` mit den
  `passwordCrypt`-Werten (`/opt/solvis/SolvisSmartHomeServer/`) und die
  angelernten `LearnedImages` samt generierten Laufzeitdaten
  (`/opt/solvis/SolvisServerData/`). Dieser State ist **nicht** Gegenstand
  dieses Drills. Gesichert wird er seit 2026-08-28 über die
  Zwei-Ziel-restic-Kette des Hosts (Scope `solvis`, Repo `ccu2mqtt`); den
  Weg beschreibt [runbooks/README.md](runbooks/README.md) (Aufgaben „Backup
  (Operator-State)" und „Restore"). Der geübte Restore dafür ist der
  Drill B4'''/B5''' der Etappe-2-Anleitung in `ccu2mqtt`, im Register als
  F-145 geführt — siehe §5.

Die einschlägige Ausprägung dieses Protokolls bleibt damit der
**Repo-only-Clone-Drill**, jetzt aber mit benannter Lücke statt mit einer
Nicht-Existenz-Behauptung.

## 2. Verfahren (Kommando-Kette)

Ausgeführt real (nicht als Walkthrough) in einem Temp-Verzeichnis
außerhalb des Repos; das Temp-Verzeichnis wurde nach Abschluss gelöscht.

```bash
# Quellstand erfassen
git branch --show-current          # -> feature/modernisierung
git rev-parse HEAD                 # -> SRC_HEAD
git rev-list --count HEAD          # -> SRC_COUNT

# 1. Bundle aus allen Refs erzeugen
git bundle create "$DRILL/solvis.bundle" --all
git bundle verify "$DRILL/solvis.bundle"

# 2. Aus dem Bundle klonen (Ziel-Branch)
git clone -b feature/modernisierung "$DRILL/solvis.bundle" "$DRILL/clone"

# 3. Zielstand gegen Quellstand prüfen
git -C "$DRILL/clone" rev-parse HEAD        # -> CLONE_HEAD
git -C "$DRILL/clone" rev-list --count HEAD # -> CLONE_COUNT

# 4. Temp restlos entfernen
rm -rf "$DRILL"
```

## 4. Abweichungsliste (Findings)

- **base.xml-„Secrets" sind kein versionierter Live-State (dokumentiert,
  kein Blocker).** Die versionierte `rsc/de/sgollmer/solvismax/data/base.xml`
  ist eine **Vorlage** aus dem Upstream. Ihre credential-tragenden Felder
  (`account`, `passwordCrypt`, `url` der Unit; `passwordCrypt` der
  `ExceptionMail`; MQTT-`brokerUrl`) enthalten **Upstream-Beispiel- bzw.
  Platzhalterwerte**, nicht die Zugangsdaten dieses Betriebs. Die **realen**
  Anlagen-/Mail-/Broker-Zugangsdaten sind **nicht-versionierter
  Operator-State**: Der Operator befüllt eine Kopie der Vorlage, die per
  `make installSolvis` nach `/opt/solvis/SolvisSmartHomeServer/base.xml`
  (`640 root:solvis`, bei jedem Lauf per `enforceOwnership` durchgesetzt)
  installiert wird; die Laufzeitdaten liegen
  daneben unter `writablePathLinux` (`/opt/solvis/SolvisServerData/`).
  Bundle und Clone tragen daher **keinen Live-Secret** — der
  Drill bestätigt das (Klon enthält ausschließlich die Vorlagenwerte).
- **Rest-Beispiel-Chiffrat im Template (Nachziehkandidat, kein Blocker).**
  Die Unit-Zeile der Vorlage führt weiterhin ein aus dem Upstream geerbtes
  `passwordCrypt`-Beispiel-Chiffrat statt eines neutralen Platzhalters
  (`account`/`url` sind bereits Platzhalter). Da die AES-Ableitung im Code
  fest ist, ist ein Chiffrat prinzipiell kein Geheimnis-Ersatz. Empfehlung:
  bei nächster Vorlagen-/Template-Pflege durch einen sprechenden
  Platzhalter ersetzen, damit „base.xml == reine Vorlage, Geheimnis ==
  Operator-State" auch feldweise gilt. Bewusst **nicht** in diesem Commit
  geändert (Upstream-Diff klein halten; Template/Parsing berührt
  control.xml-/Dual-Parse-Testfläche → nur mit grünem TESTPLAN-Nachweis).

Phase-2-Gate-Check dieses Projekts sowie nach jeder Änderung an der
Repo-/Backup-Topologie.

**Offener Posten aus der Produktivaufnahme (Register F-145, Frist
2026-08-31):** Mit dem Cutover am 2026-08-13 ist erstmals Operator-State
entstanden (§1). Nach dem Standard `wiederkehrende-verifikation.md` §2
Klasse (a) ist das eine Änderung der Backup-Topologie und verlangt einen
eigenen Restore-Drill. Der Registereintrag dazu existiert seit 2026-08-17 als
F-145 (Anleitung `ccu2mqtt:docs/runbooks/solvis-bridge-restore.md`); die
Lücke wird über die Host-Kette geschlossen, nicht über den tar|age-Handexport.
Der einschlägige Drill ist B4'''/B5''' der Etappe-2-Anleitung
(Restore aus beiden Zielen, dann `solvis`-Snapshot je Ziel — Beleg in
`ccu2mqtt/docs/status.md` §4 Punkt 30, Ablauf in
`ccu2mqtt/docs/runbooks/haus-hosts-backup.md` §1.3 Zeilen R-4/R-5). Zum
Drill gehört der Nachweis, dass `base.xml` nach dem Rückspielen wieder
`640 root:solvis` trägt (Restore-Schritt 3 im Runbook) und die angelernten
Bilder ohne erneute Lernphase tragen. Bis dieser Beleg vorliegt, ist der
Operator-State **UNVERIFIED**; der Status wandert erst mit dem eingetragenen
Snapshot-Beleg.
